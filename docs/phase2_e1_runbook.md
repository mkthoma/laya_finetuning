# Phase 2 runbook: E1 first real run and the gate (Colab T4 via VS Code)

This runbook covers `notebooks/e1_first_run.ipynb`. The notebook runs Phase 2 of the design doc
(`Laya Record-Normalisation PoC.md` §6.2) on a free Colab T4: the FULL frozen data, the B1/B3 baselines, zero-shot
`laya`, E1 (`laya`, seed 11, 25k train questions x 4 epochs, resumable, with one forced crash and resume), the
temperature fit, the evaluation on `val`, a CPU benchmark and the **gate** that decides whether Phase 3 may spend money.
Expected runtime: about **2.5-3.5 h** (E1 itself about 2-2.3 h).

Entry conditions (design doc §6.2): the Phase 1 smoke test passed (`docs/results/phase1_smoke_report_2026-09-26.md`,
8/8), and the full splits are frozen: `config.yaml` → `data.frozen_manifest` names the fingerprint manifest
(`docs/results/data_fingerprint_2026-09-15.json`) written by the first FULL build. Step 5 rebuilds the data on Colab
and fails unless every JSONL file hashes exactly as in that manifest.

The notebook is generated by `tools/build_e1_notebook.py` and embeds the project code (and the frozen manifest) as a
checksummed bundle. **After changing any code or `config.yaml`, regenerate it**; `tests/test_build_e1_notebook.py`
fails while the committed notebook is stale.

| Need | Detail |

| Disk | Step 4 requires 20 GiB free. E1 keeps 2 resumable checkpoints (about 5 GB each) plus `best/` and `final/` (about 0.9 GB each, fp16) |

Optional: run the plumbing locally first (no GPU, a few minutes). See §8.

## 2. Build and connect

```bash
.venv/Scripts/python tools/build_e1_notebook.py            # writes notebooks/e1_first_run.ipynb (token prompt in Step 3)
.venv/Scripts/python tools/build_e1_notebook.py --with-token   # unattended: gitignored notebooks/e1_first_run.local.ipynb
```

The unattended variant reads `HF_TOKEN=hf_...` from the repo's `.env` (gitignored) and puts it into Step 3 of the
gitignored `.local.ipynb` copy. Never share, upload or commit that file; rebuild it after any code change. With a token,
`--out` must be a gitignored `notebooks/*.local.ipynb` (or a `*.local.ipynb` outside the repo); anything else is refused.

Connect exactly as for the smoke test: **Select Kernel → Colab → New Colab Server → GPU → T4**, then the Python 3
kernel. **Not Auto Connect** (it gives a CPU server and Step 4 fails). If the extension silently assigns another GPU,
E1 still trains with the T4 batch profile (`--card T4`: micro-batch 8 x accumulation 4), so the step plan, the
checkpoint cadence and the forced crash stay as planned; only the time, VRAM and the speed rows stop describing a T4.

## 3. Run it (unattended)

Click **Run All** and leave it. Every step is idempotent: a finished step is skipped (`skip: ... exists`) on a re-run,
so Run All is also the way to continue after a kernel restart (§5). `REDO = True` in Step 1 recomputes everything,
**including E1 from scratch**. Full logs are in `/content/laya_poc/runs/e1/logs/`; cell output is sparse on purpose.

E1's plan on the T4 profile: 3344 micro-steps per epoch (ceil(25000 x 1.07 / 8)), 13376 micro-steps and 3344 optimiser
steps over 4 epochs, 13 periodic evals (plus the initial one at opt step 0), 6 resumable checkpoints of about 72 s
each. At the smoke test's 0.43 s per micro-step that is about 1.6 h of training plus about 15 min of evals and
checkpoints. Early stopping (patience 3 evals, min delta 0.002 macro-F1, `config.yaml` `train`) may end it sooner.

## 4. The forced resume (Steps 8-9)

The gate needs "at least one real resume observed or forced". It is forced so it never depends on luck:

- Step 8 starts E1 from an empty `runs/e1/train`, checkpoints at micro-step 2000 and hard-kills itself (SIGKILL) right
  after micro-step 2002 (`e1.crash_at_micro_step`). The cell expects exit code -9 or 137, writes `crash_exit.json`, and
  checks that `train/log.jsonl` holds the injected crash at micro-step 2002. Any other exit stops there with the log
  tail: a CUDA OOM, or a kill without `crash_injected` (usually the host OOM killer; check `free -h`, `dmesg | tail`).
- Once the crash has happened, Step 8 **skips itself** (it never restarts E1), so Run All after a restart is safe.
- Step 9 refuses to run before that crash ("run Step 8 first"), then resumes: its log must contain
  `resumed from ...` (micro-step 2000). Each attempt gets its own log (`09_e1_resume.log`, `_2.log`, ...).
- Crash and resume share every setting; `train_single` refuses a resume whose settings differ. For a CUDA OOM, add
  `"--micro-batch", "4", "--effective-batch", "32"` to `cmd` in **both** Steps 8 and 9, delete
  `runs/e1/crash_exit.json` (Step 8 then starts E1 afresh instead of skipping itself), and run Steps 8 and 9. Do not use
  `REDO = True` for this: with Run All it would also redo the data, the baselines and the zero-shot steps.

## 5. After a disconnect or a kernel restart

E1 is resumable at any micro-step: everything it needs (weights, optimiser, scheduler, scaler, early-stopping state,
`best/`) is in the newest checkpoint, and the batches replay deterministically.

1. Reconnect VS Code to the **same** server (Select Kernel → Colab → the existing alias). If the cell is still shown as
   running, the kernel survived: do nothing, training continues.
2. If the kernel restarted: re-run **Step 1**, then **Step 9** (or Run All: Steps 2-8 skip themselves). Step 9 resumes
   from the newest checkpoint, so at most 2000 micro-steps (about 14 min) are redone. Steps 8 and 9 refuse to start
   while a trainer from before the restart is still running (Linux `/proc` check): wait for it to stop, or stop it
   with `os.kill(pid, 9)` in a cell (checkpoints are written atomically), then re-run.
3. If Step 1 prints `HF token: not set yet`, run Step 3 before Step 9 (only Step 5 needs the token).
4. If the server itself was removed (idle timeout, 12-hour limit, Remove Server), `/content` is gone with every
   checkpoint: start again from Step 1 on a new server; E1 restarts from scratch in Step 8.

A running cell keeps the server alive. Answer an `"<alias>" is idle` toast with **Cancel** within 10 s.

## 6. Reading the gate (Step 13)

The first line is the verdict: `PASS` only when all four criteria pass (thresholds in `config.yaml` → `gate`; points
are macro-F1 x 100). A missing or unreadable input fails its criteria with a note; the report never crashes.

| # | Criterion | Pass condition | Inputs |
|---|---|---|---|
| 1 | End-to-end | training finished (`stop_reason` epochs, early_stop or max_micro_steps), temperature fit passed (`export_check.json` `passed`), val evaluation done, CPU benchmark with at least one thread setting, and at least one `resumed` event in `train/log.jsonl` | `train/summary.json`, `train/log.jsonl`, `export_check.json`, `eval_e1_val.json`, `bench_cpu.json` |
| 2 | Numerics | 0 non-finite losses; 0 optimiser steps that applied a non-finite gradient; min GradScaler scale >= 1. Steps GradScaler **skipped** (inf/NaN gradients, scale halved) are expected in fp16 and only reported | `summary.json`, `log.jsonl` |
| 3 | Beats trivial | E1 `val` macro-F1 (post-T) >= zero-shot `laya` + 10 points and >= B1 majority + 20 points | `eval_e1_val.json`, `eval_zeroshot_val.json`, `baselines.json` |
| 4 | Near TF-IDF+LR | E1 `val` macro-F1 >= B3 TF-IDF+LR (post-T) - 5 points | `eval_e1_val.json`, `baselines.json` |

The **headline** macro-F1 is 10-class, or 9-class (Event excluded from the average) when the ID pool has fewer than
`labels.event_min_id_pool` (300) labelled Event places: `data_report.json` → `headline_classes` (design doc §5.2).
Every comparison uses the same headline metric.

Information rows (no pass/fail): E1 val metrics (acc, ECE, acc@80/90, abstentions), wall-clock over the crash and
resume processes, seconds per micro-step and peak VRAM, stop reason and epochs, best opt step, T and ECE pre -> post,
B3's C and T, zero-shot `laya-multilingual` if run, the data fingerprint and whether it matches the frozen manifest,
and the trap-candidate count ("annotation pending"). The CPU table compares p95 latency and records/s with
`cpu_budget` for information only: the decision rule's CPU budget is judged in Phase 5 on 4 vCPUs with ONNX.

**On FAIL** the report (and the cell) lists the design doc's debug checklist: stop and debug before any spend.
Check the leakage asserts (`data_report.json`), the label mapping, the question-key order, the truncation counts
(`summary.json` `truncated_items`), the learning rates (`opt` events) and the loss sign (`micro` and `eval` events).

## 7. When something fails

| Symptom | Likely cause and fix |
|---|---|
| Step 2: `duckdb ... != pinned ...` | pip could not install the pinned DuckDB; read `logs/02_install_duckdb.log`. Do not build the data with another version: the frozen splits depend on its `hash()` |
| Step 4 errors | As in the smoke test runbook §6 (CPU server, no `sm_75` kernels, Laya commit, disk) |
| Step 5: 401/403 | Dataset terms not accepted or wrong token: accept them on the Hub, set `ASK_AGAIN = True` in Step 3, re-run it, then Step 5 |
| Step 5: `data differs from the frozen manifest` | This build is not the frozen E1 data. Compare `data_report.json` versions (DuckDB, pandas, pyarrow) with the manifest; do not train on it. Re-freeze only deliberately (`build_data --write-manifest`, then update `data.frozen_manifest` and rebuild the notebook) |
| Step 5: `frozen manifest ... not found` | The notebook was built before the manifest existed; rebuild it (`tools/build_e1_notebook.py`) |
| Step 5: DuckDB memory or httpfs errors | Re-run Step 5 (spills to disk). Lower the memory with `"--duckdb-memory", "4GB"` in its `cmd` if the host OOM killer struck |
| Step 7/10/11: `CPU fallback` | A CUDA OOM made Laya answer a batch on CPU: restart the kernel, delete the step's JSON, add `"--batch-size", "16"` to its `cmd`, re-run |
| Step 8 or 9: CUDA OOM | See §4: `--micro-batch 4 --effective-batch 32` in Steps 8 **and** 9, delete `runs/e1/crash_exit.json`, run Steps 8 and 9 |
| Step 8: exit 0 | The crash flag never fired (the run ended before micro-step 2002?); read `logs/08_e1_crash.log` |
| Step 8: `killed ... but not as planned` | Something else killed it (host OOM killer); check RAM and `dmesg`, then re-run Step 8 |
| Step 9: `run Step 8 first` | The forced crash has not happened (or `crash_exit.json` is missing); run Step 8 |
| Step 9: no `resumed from` | No checkpoint in `runs/e1/train/ckpt/`: check disk (`env.json`), `logs/08_e1_crash.log` |
| Step 9: aborts on `max-nonfinite` | NaN/inf losses (design doc §9 "NaN or inf loss"); the gate would fail numerics anyway |
| Step 10: `passed: false` | Read `train_eval`, `budgets` and `roundtrip_max_dp` in `export_check.json`; the gate fails end-to-end |
| Step 12: fewer thread settings than asked | `bench_cpu.json` → `errors`; one setting is enough for the gate |
| Step 12: `exited with 1`, 0 thread settings | Every setting failed (`bench_cpu.json` → `errors`, `logs/12_bench_cpu.log`), e.g. `best/` incomplete. Fix the cause and re-run Step 12: it re-runs until `bench_ok.json` exists, the failed `bench_cpu.json` does not make it skip |
| Gate FAIL on criteria 3-4 | Stop and debug before any spend (§6); do not start Phase 3 |

## 8. Local dry run (no GPU)

```bash
.venv/Scripts/python tools/dry_run_e1_local.py [--work <dir>] [--tiny-ckpt <existing tiny checkpoint dir>]
```

It executes the **same cells** (Step 1, Steps 4-13, 14a/14b) on CPU with a tiny random Laya checkpoint (init scale 0.5,
so it can learn a little; needs Hub access for the tokenizer), a synthetic FULL-mode pool (all 15 countries, brand
chains, trap-word names, mixed-level-1 rows) passed with `--pool`, and tiny sizes (120 train rows, 2 epochs, an eval
every 2 opt steps, a checkpoint every 8 micro-steps, the crash at 10). Early stopping is off (`train.patience`
1000000), so E1 crosses the epoch boundary (`train_e1.jsonl`, epoch 1's sigma and batch order) and ends naturally
(`stop_reason` `epochs`, final eval, `final/` and `best/`). Gate criteria 1-2 (end-to-end, numerics) must pass and E1
must train every planned micro-step, else it exits 1; 3-4 are not meaningful on a tiny model. The test
`test_dry_run_end_to_end_passes_the_plumbing_criteria` runs it when `LAYA_DRY_RUN_TEST=1`.

## 9. After the gate

1. Copy the gate table and the information rows into the results workbook; keep `gate_report.md`.
2. Download `e1_artifacts.zip` (Step 14a: logs, JSON, markdown, the FSQ NOTICE; no checkpoints, no FSQ rows).
   `COPY_BEST_TO_DRIVE = True` also copies `best/` (with its NOTICE files) to Drive if you want to keep E1.
3. Run **Colab: Remove Server**. It deletes `/content`, checkpoints and the saved token included.

**Pending human task (not part of the gate): trap annotation** (design doc §5.3). `data/trap_candidates.csv` holds
FSQ rows (download it for the annotators only if the FSQ terms allow it for your team; never commit it). Two
annotators fill `keep_a1` / `keep_a2` (1 = the FSQ label is plausibly right AND the name misleads), the lead fills
`keep_lead` where they disagree, then:

```bash
python -m laya_poc.traps merge --candidates data/trap_candidates.csv [annotator2.csv] --out data/trap.jsonl
```

Every candidate was removed from every split before E1, so whatever is kept is unseen by every run.

**What Phase 3 needs** (design doc §5.14, §6.2; only after a gate PASS and budget approval): a Colab L4 (preferred,
Colab Pro) or a rented A10 (`--card L4` / `A10`: micro-batch 32 x 1, no gradient checkpointing); the same frozen data
(Step 5 verifies it); E2 = `laya` seeds 22 and 33, E3 = `laya-multilingual` (`--model laya_ml`) seeds 11/22/33, then
E4-E6; the trap set merged before the Phase 5 evaluation.

## 10. What only the Colab run can confirm

- The FULL extraction fits Colab (12.7 GB RAM, 2 vCPU) in 10-20 min and reproduces the frozen fingerprint on Linux.
- E1's real speed, VRAM and eval cost over 4 epochs at MB 8 (the smoke test measured 250 micro-steps), and whether
  early stopping ends it before epoch 4.
- Whether GradScaler skips any fp16 steps over 13k micro-steps and whether its scale stays >= 1.
- The accuracy criteria themselves: E1 vs zero-shot, majority and TF-IDF+LR on the real `val` split.
- The CPU benchmark on Colab's 2 vCPUs, and the time B3 needs there.
- How the VS Code Colab extension behaves on a multi-hour cell: idle toasts, reconnecting to a running kernel.
