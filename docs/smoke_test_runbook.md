# Phase 1 smoke test runbook (Colab T4 via VS Code)

This runbook covers `notebooks/smoke_test.ipynb`. The notebook proves on a free Colab T4 that the single-GPU
fine-tuning port works end to end before any paid run. It implements Phase 1 of the design doc
(`Laya Record-Normalisation PoC.md` §6.2) with the exit criteria restated in `config.yaml` → `smoke.exit`.

The notebook is generated by `tools/build_notebook.py`, and the project code is embedded in it as a checksummed
bundle. **After changing any code or `config.yaml`, regenerate the notebook** (`python tools/build_notebook.py`).
Otherwise Colab runs the old code (`tests/test_build_notebook.py` fails when the committed notebook is stale).

## 1. Before you start

| Need | Detail |
|---|---|
| VS Code | Extensions **Google Colab** (`google.colab`, 0.9.6 or newer) and **Jupyter** (2025.x or newer) |
| Google account | Free Colab tier is enough; the smoke test fits well inside one session |
| Hugging Face | An account that has **accepted the terms of the gated dataset** `foursquare/fsq-os-places`, and a **read** token for it (huggingface.co/settings/tokens) |
| Time | About 60-90 minutes with VS Code open and the laptop awake the whole time. Step 7 (parity) is the longest step, about 25-35 min |

Optional: run the plumbing locally first (no GPU, about 5 minutes). See §7.

## 2. Connect to a T4

1. Open `notebooks/smoke_test.ipynb` in VS Code.
2. Click **Select Kernel** (top right) → **Colab** → **New Colab Server**.
3. Choose **GPU**, then **T4**. Choose shape *Standard* if asked. For the runtime version pick *Latest*, or *2026.07* for
   Python 3.12 / torch 2.11 / transformers 5.13 (both are supported, and the versions are recorded). Accept the alias.
4. Sign in with Google in the browser when asked, then pick the **Python 3** kernel.

Pitfalls:
- **Do not use *Auto Connect*.** It creates a CPU server, and Step 4 then fails with "no CUDA GPU". Fix: run **Colab:
  Remove Server**, then repeat the steps above.
- If no T4 is free, the extension may **silently assign another GPU** (a toast says `Requested accelerator "T4" is
  unavailable`). The notebook still runs: Step 4 warns, and Steps 8-10 pass `--card T4`, so every card trains with the
  T4 profile (micro-batch 8 x accumulation 4). That keeps the plan intact: 250 micro-steps, a checkpoint every 40, the
  kill at 122 and the resume from 120. The card's own profile would break the plan: an L4 or A10G would get micro-batch
  32 x 1 and stop near micro-step 67, before the crash, and an A100 or H100 has no profile at all. The report records the
  card. VRAM and throughput then do not describe a T4, so for the real smoke test prefer **Colab: Remove Server** and
  retry later.
- "Unable to assign server. You have too many" → remove an old server (**Colab: Remove Server**).
  "insufficient quota" → the free GPU quota is used up; try again later.

## 3. Run it

Click **Run All**, or run the cells one by one. Each code cell starts with a `# Step N` comment, and a markdown
heading above it explains the step.

- **The token prompt** (Step 3) is a masked input box at the **top of the VS Code window**, not in the cell. Paste the
  token and press Enter. Esc sends an empty string, which the cell rejects. The token is validated with the Hub,
  saved in the runtime's own token file (`~/.cache/huggingface/token` on the server) and never printed. It is not stored
  in the notebook and disappears with the server.
- **Unattended run (no prompt):** put `HF_TOKEN=hf_...` in the repo's `.env` (gitignored), run
  `.venv/Scripts/python tools/build_notebook.py --with-token`, and open `notebooks/smoke_test.local.ipynb` instead of
  `smoke_test.ipynb`. That copy carries the token in Step 3 (never printed) and is gitignored: do not share, upload or
  commit it, and rebuild it after any code change. The only remaining manual step is picking the Colab T4 kernel.
- A running cell keeps the server alive. Do not close VS Code, let the laptop sleep, or lose the network. If an
  `"<alias>" is idle. It will soon be removed` toast appears, press **Cancel** within 10 s.
- Output is sparse on purpose because VS Code truncates long outputs. Every command's full output is in
  `/content/laya_poc/runs/smoke/logs/<NN_step>.log`. Open it from the Colab view in the activity bar (Contents), or print
  it from a cell.
- **After any kernel restart** (a crash, a manual restart, the kill drill), re-run **Step 1 (Setup)** first, then
  continue. Steps whose output already exists are skipped (`skip: ... exists`). To redo them, set `REDO = True` in
  Step 1 and re-run it.
- **Steps 9 and 10 are one drill.** Step 10 resumes only once per crash: it refuses to run when `resumed/log.jsonl` does
  not end at the injected crash, for example after an interrupted Step 10 or a second run with `REDO = True`. A second
  resume would restart from a later checkpoint, and the report would grade that one. Step 9 empties `runs/smoke/resumed`
  and starts the drill again. It is skipped once `resumed/summary.json` exists, that is, after Step 10 has finished.
  - If Step 10 was interrupted, re-run Step 9, then Step 10.
  - If Step 10 had finished, first set `REDO = True` in Step 1 and re-run Step 1.

## 5. Reading the report (Step 12)

The first line is the verdict: `PASS` only when every exit criterion passes. The checklist rows are:

1. **Parity** (per checkpoint): max |Δp| ≤ 0.02, argmax agreement ≥ 0.995, no NaN, padded vs unpadded within 0.02.
   A test agent that ran on CPU, or that answered any batch on CPU after a CUDA OOM (`cpu_fallback`), never passes.
2. **Crash exit**: the crash run ended with a non-zero code (-9 or 137 expected) after the injected crash at
   micro-step 122.
3. **Resume point**: the resumed run restarted from the last checkpoint at or before the kill (micro-step 120).
4. **Resume fidelity**: the mean `loss_ce` over micro-steps 121-140 is within 2% of the control run's, and the
   learning rates and GradScaler scale of every later optimiser step match the control run. CUDA kernels are not
   bit-deterministic, so the loss test compares a 20-step mean.
5. **Loss drop**: the control run's held-out val CE (200 labelled val rows, eval mode) falls by at least 10% from the
   initial eval (`--initial-eval`, opt step 0) to the final eval. Per-micro-batch training loss depends on which
   batches land in a window, so the training-loss windows are shown as information only.
   *Deviation from the design doc (§6.2 says 20%), decided 2026-09-26:* a CPU run of the real 421M model with the
   doc's learning rates reached only about 19% in the smoke run's 63 optimiser steps, so 20% would fail a correct
   trainer about half the time. 10% still separates a learning trainer from a broken one. The report also states
   whether the doc's 20% was met (`smoke.exit.doc_loss_drop`, information only).
6. **Numerics**: no non-finite loss, and the GradScaler scale stays ≥ 1.
7. **VRAM**: peak `torch.cuda.max_memory_reserved` ≤ 14 GB (10^9 bytes).

The information rows (no pass/fail) hold the GPU/driver, versions and Laya commit, zero-shot correct/20 per checkpoint,
seconds per micro-step, and the **extrapolated E1 wall-clock** (training, evaluation and checkpoint time). Copy them
into the §7.13 "Smoke test" results table.

Licence and attribution (design doc Appendix D): `data/NOTICE_FSQ.txt` carries the FSQ NOTICE text verbatim plus the
statement that the data was modified (its sha256 is in `data_report.json`). The fine-tuned checkpoint
`control/final/` carries `NOTICE.md` (base checkpoint, "modified: fine-tuned", Laya's Apache-2.0 licence),
`NOTICE_FSQ.txt` and Laya's `LICENSE`. Keep these files with anything you keep from the run.

## 6. When something fails

A failing step raises an error that names its log file, and for the common causes it adds a `hint:` line. Read the log
first. Design doc §9 has the full troubleshooting list; the mapping is:

| Symptom | Likely cause and fix (§9 item) |
|---|---|
| Step 4: `no CUDA GPU` | Auto Connect or CPU server. Remove Server, reconnect with GPU → T4 (§2) |
| Step 4: `torch ... has no kernels for this GPU (sm_75 ...)` | The runtime's torch build lacks T4 (`sm_75`) kernels. Another T4 does not help: Remove Server and start a New Colab Server on another runtime version (e.g. *2026.07*, §2) |
| Step 4: `laya commit ... != pinned ...` or `laya is not installed` | Step 2 did not run or failed; re-run Step 2 and read `logs/02_install_laya.log` |
| Step 4: `only ... GiB free disk, need >= 20 GiB` | The crash run keeps up to three 5 GB checkpoints. Delete old checkpoints (Step 13b, `CLEANUP_CKPTS = True`) or Remove Server and start a new server |
| Step 4: `environment check failed: no env.json written` | env_check itself crashed; read `logs/04_env.log` and `runs/smoke/env.json.traceback.txt` |
| Step 2: `pip changed {...}` (torch, transformers, protobuf or numpy) | A dependency forced an upgrade. Remove Server, start again, report the log |
| Step 5: 401/403 | Dataset terms not accepted, or wrong token (§9 "401/403"). Accept the terms on the Hub; for a new token set `ASK_AGAIN = True` in Step 3 and re-run it; then re-run Step 5 |
| Step 5: DuckDB/httpfs errors, rate limits | Re-run Step 5 (§9 "DuckDB / httpfs") |
| Step 5: "country returned 0 rows" | The best-file map in `config.yaml` (`smoke.best_files`) does not fit this FSQ release; recompute it (see `extract.best_files_by_country`) |
| Step 7: parity FAIL or NaN | fp16 attention numerics on the T4 (design §8). Re-run the failing checkpoint's command with `"--attn", "eager"` added, delete its `parity_*.json`, and compare. Record both results; do not train until parity passes |
| Step 7 or 11: `CPU fallback` in the PASS/FAIL line (`cpu_fallback: true`) | Laya hit a CUDA OOM on a batch and answered it on CPU in fp32, so the result is not a GPU check. Free GPU memory (restart the kernel, or Remove Server), delete the step's JSON (`parity_*.json` or `export_check.json`), add `"--batch-size", "8"` to its `cmd` and re-run the step |
| Step 8: CUDA OOM | §9 "CUDA OOM": add `"--micro-batch", "4", "--effective-batch", "32"` to `cmd` (grad checkpointing stays on for T4), re-run Steps 8-10 with the same flags |
| NaN/inf loss, run aborts on `max-nonfinite` | §9 "NaN or inf loss". Check `control/log.jsonl` micro events (`finite`, `scale`) |
| Loss does not fall | §9 "Loss stuck or zero": check labels/gold in `data/`, LRs in `config.yaml` |
| Slow micro-steps (> 1.5 s at MB 8) | §9 "Slow steps": padding ratio in the `start` log event, grad checkpointing |
| Step 9: exit code 0 | The crash flag did not fire (the run finished before micro-step 122?). Check `logs/09_crash.log` |
| Step 9: `the crash run was killed (-9) but not as planned` | Something other than the injected crash killed it, usually the host OOM killer (the error shows the log tail). Check RAM (`free -h`) and the kernel log (`dmesg \| tail`), then re-run Step 9 |
| Step 10: no `resumed from` | No checkpoint survived in `runs/smoke/resumed/ckpt/`. Check disk space (`env.json` → `disk_free_gb`) and `logs/09_crash.log` |
| Step 10: `the crash/resume drill is incomplete` | A resume already ran or was interrupted, or the crash run did not end with -9/137. Re-run Step 9, then Step 10. Set `REDO = True` in Step 1 first if Step 10 had finished (§3) |
| Step 3: `the Hub rejected the token (HTTP 401/403)` | Wrong or revoked token. Set `ASK_AGAIN = True` at the top of Step 3, re-run it and paste a new token |
| Step 3: `could not reach the Hub` | Network or DNS problem on the server. Re-run Step 3. If a different token is needed, set `ASK_AGAIN = True` |
| Step 11: temperature clamped | §9 "Temperature looks clamped". Informational for a 250-step model |
| Kernel died during a step | Wait for the automatic restart (or run **Jupyter: Restart Kernel**), re-run Step 1, then the failed step (for Step 10, re-run Step 9 first: §3). Check for orphaned GPU processes with Step 13d |
| Interrupt/Restart greyed out or hung | Known extension issue; **Colab: Remove Server** and start again (all state on the server is lost) |

### Optional steps (13a-13d)

- **13a Archive** (on by default): zips logs, JSON, the report and `data/NOTICE_FSQ.txt` (no checkpoints, no FSQ
  rows) to `/content/laya_poc/smoke_artifacts.zip`. The NOTICE file is the FSQ NOTICE text verbatim plus the statement
  that the data was modified, which design doc Appendix D requires with every kept FSQ-derived artefact. Download it from the Colab view in the activity bar: **Contents** →
  right-click → **Download...**. Set `COPY_TO_DRIVE = True` to also copy it to `MyDrive/laya_poc`. That needs an
  interactive Google sign-in (about 2 minutes to finish) and fails for some Workspace accounts.
- **13b Free disk**: `CLEANUP_CKPTS = True` deletes `runs/smoke/*/ckpt` (about 5 GB per checkpoint; only the crash run
  writes them); `final/` is kept.
- **13c/13d Kernel-kill drill** (off by default). Checks what the crash drill in Steps 9-10 cannot: whether `/content`
  and site-packages survive a hard kernel kill, and whether a child process holding the GPU dies with the kernel.
  1. Set `KILL_DRILL = True` in 13c and run that cell. It starts a child that holds a CUDA context, records both PIDs in
     `runs/smoke/kill_drill.json`, then SIGKILLs the kernel. VS Code reports that the kernel died; this is expected, and
     any queued cells are cancelled.
  2. Wait for the automatic restart (or run **Jupyter: Restart Kernel**). Run **Step 1**, then **Step 13d**.
  3. 13d prints PASS/FAIL for each check and writes `kill_drill_result.json`.
     - "/content survived" passes only when `kill_drill.json` is still there and the sentinel is the original one.
       Step 1 recreates a missing sentinel with a new timestamp. 13c also writes a copy of the record outside
       `/content` (`~/.laya_poc_kill_drill.json`), so a wiped `/content` shows as FAIL rather than "no drill".
     - It kills only the drill's own child, recognised by a marker in its command line, and never the kernel.
       nvidia-smi may report host PIDs, so it lists any other GPU process without touching it.
     - An orphan means a training run interrupted by a kernel crash can keep holding VRAM. Record the result.

## 7. Local dry run (no GPU)

```bash
.venv/Scripts/python tools/dry_run_local.py            # Windows; use .venv/bin/python elsewhere
.venv/Scripts/python tools/dry_run_local.py --work <dir> --tiny-ckpt <existing tiny checkpoint dir>
```

The dry run executes the **same cells** as the notebook (Step 1, Steps 4-12, 13a/13b/13d) on CPU. It uses a tiny random
Laya checkpoint (built like the tests' `tiny_ckpt_dir`; needs Hub access for the tokenizer), a synthetic pool
(`--pool`), `--allow-cpu`/`--device cpu`, and tiny sizes: 24 micro-steps, a checkpoint every 8, a crash at 10. It ends
with the report path and a verdict. The verdict is FAIL by design: CPU parity never counts as a GPU check, a random
tiny model does not learn in 24 steps, and there is no VRAM. The run proves that the plumbing between the CLIs works.
Takes about 4-5 minutes on a laptop. The test `test_dry_run_end_to_end` runs it when `LAYA_DRY_RUN_TEST=1`.

## 8. Finish and clean up

1. Check the verdict and copy the report values into the §7.13 template.
2. Download `smoke_artifacts.zip` (13a).
3. Run **Colab: Remove Server**. This stops quota use and deletes `/content`, including checkpoints and the saved token.

## 9. What only the Colab run can confirm

These are inferred from source or docs, not observed. The smoke test is where they get confirmed:
- `getpass` shows the masked VS Code input box and the value reaches the kernel.
- `sm_75` is in `torch.cuda.get_arch_list()` on the chosen runtime (CUDA 13 images).
- fp16 SDPA with ModernBERT sliding-window masks on sm_75 gives no NaN and passes parity; if not, whether `--attn eager` fixes it.
- `os.kill(os.getpid(), SIGKILL)` inside the training process yields exit code -9 through `subprocess.Popen`.
- Peak VRAM, seconds per micro-step and the checkpoint save time on a T4 (about 5 GB per resumable checkpoint).
- After a hard kernel kill: automatic restart, `/content` and site-packages survive, and no orphaned GPU process remains (13c/13d).
